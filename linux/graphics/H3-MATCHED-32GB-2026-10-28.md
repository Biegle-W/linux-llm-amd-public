# Matched H3 single-GPU versus actual fcys TP2 on 32 GB — October 28, 2026

**Complete; isolated candidate, no production promotion.** On this real 32 GB host, actual fcys RCCL TP2 reduced the median fresh-server request by **14.2%** (179.209 → 153.773 s). Single-GPU denoising was faster: TP2's both-ready sampler window was **1.303×** as long. These are three timed runs per arm, after one excluded warmup each, starting from saved conditioning. Text-encoder costs are excluded.

## What was matched

Hardware: 32 GB nominal / 30.558 GiB OS-visible RAM and two Radeon RX 7900 XTX cards (gfx1100). Both arms use the same frozen Comfy 0.42 source, pinned OTUNetLoaderW8A8 INT8 loader with ConvRot, CK attention, BF16 compute, CPU RandomNoise seed 42 and identical finite W4A8 native-INT8 text conditioning. Workload: 608×352, 39 frames, 24 fps, 20 res_multistep/simple steps, batch 1, cache-none. Conditioning SHA-256: `185331d00407eac923e272503456b69736c7233f69632ca83b45430c77e0bbfa`.

The single-GPU process sees physical GPU0 only; all diffusion and AV decode work stays there. TP2 uses the original pinned fcys two-rank source with RCCL, P2P disabled, Simple protocol, one channel and 1 MiB buffers. Each rank sees its own one physical GPU. Rank0 loads its diffusion model before rank1 is admitted, reducing simultaneous CPU checkpoint residency. Rank0 alone decodes/saves AV; rank1 exports finite sampled latents. Loader/module identities, visibility, fixture hashes and graph settings are checked in every completed run. No fcys source is redistributed.

Every generation uses fresh servers and unique owned scopes. Natural OS file caches and paging are retained; this is not a controlled cold-file benchmark or persistent-resident benchmark. The same original diffusion and VAE payloads are read from Shared SATA storage. New timings exclude text-encoder loading/encoding; the [completed encoder-format comparison](H3-AMD-ENCODER-FORMATS-2026-10-28.md) remains separate. Common source, loader and CPU noise narrow the earlier comparison's confounders; distributed rank lifecycle/numerics still differ, so this is not a GPU-count-only or pure-kernel scaling result.

## Timing interpretation

Request time runs from graph preparation/submission to successful histories observed on all participating ranks. It includes disk/model loading, serialized rank arrival, denoising, AV decode/save and history polling; server readiness and teardown are outside it. Lifecycle time covers owned worker startup through verified shutdown, excluding the later CPU media validation and between-run waits.

GPU-synchronized sampler spans use the latest rank start to latest rank end for the both-ready window. The earlier rank's wait while the other loads is shown separately. TP2 rank0's full sampler-call span therefore includes that wait. The retained per-rank spans do not measure pure GPU kernel time.

GPU-load columns sum `load_models_gpu` calls only; checkpoint parsing/materialization before those calls is outside them. AV decode sums video/audio `VAE.decode` calls and includes nested GPU loading. Columns overlap and do not sum to request time. Full-request differences are substantially outside the both-ready sampler window, but these spans do not isolate every loader/storage cost or prove a single causal mechanism.

## Quality and limits

All eight outputs pass full AV decoding: 608×352, 39 unique frames at 24 fps (1.625 s), stereo 32 kHz audio and finite decoded PCM. TP2 rank1 sampled latents are finite. First/middle/last frames of all eight clips were visually reviewed: coherent red ceramic teapot, pale wood, soft green plant background and evolving steam, without obvious sampled corruption/text/logos. Steam attachment to the spout is only partial. This is sampled visual acceptance, not exhaustive motion or semantic audio qualification.

Repeatability evidence including warmups: one: 1 distinct decoded-video hash(es) and 4 distinct PCM hashes across four clips; tp2: 2 distinct decoded-video hash(es) and 4 distinct PCM hashes across four clips. Single-GPU decoded video reproduced byte-for-byte across its four clips; TP2 produced two decoded-video variants. The arms have different video hashes, and audio did not reproduce byte-for-byte in either arm. Shared seed/conditioning does not establish bitwise parity across execution paths. This one prompt, one seed and short 39-frame workload do not qualify long video, maximum resolution/capacity or production use.

The initial source snapshot omitted a nested package and failed before generation. Both failed setup attempts cleaned up; their evidence is retained as harness failures, not model/RAM failures. The corrected R2 inventory verified 1,026 Python source files with only the intended phase observer differing; all frozen harness hashes were preserved through the run series.

The [earlier host-staged comparison](H3-ONE-VS-TWO-2026-10-28.md) uses a different implementation and retains its own numbers and limits. Native [Radiance gfx1100 compatibility](RADIANCE-H3-PREFLIGHT-2026-10-28.md) remains a separate kernel blocker. Model payloads, production selection, engine pins, coordinators and paused schedules remain unchanged. This completes the requested bounded 32 GB comparison; further capacity or production qualification requires a separate workload and explicit scope.

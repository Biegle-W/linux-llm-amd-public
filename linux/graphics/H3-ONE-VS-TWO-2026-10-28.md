# Fresh H3 one-card versus two-card test — October 28, 2026

[Staged fcys low-RAM canary](H3-FCYS-LOWRAM-2026-10-28.md): the unchanged aligned 1 GiB retry still stopped while loading both encoders. One GPU encoder process, shared conditioning and rank-0-only AV decoding then completed actual TP2's 20-step/five-frame canary with at least 10.829 GiB host RAM available. Media decodes but fails the teapot prompt; no matched timing or promotion. Both isolated host checks use the requested 1 GiB floor; other guards and production settings remain.

Fresh tests completed on one physical 7900 XTX and on two 7900 XTX cards: one excluded warmup plus three timed 39-frame generations per arm, with a new isolated server for every generation. Full-request medians are 270.098 s on one card and 146.603 s on two (45.7% shorter on the two-card path). Sampler medians are 30.237/59.749 s. This establishes the measured fresh-server workflow result; loader/storage/noise/source differences limit attribution to GPU count alone. All independent guards and loading-swap-v3 remained. No production promotion or native Radiance run.

## What one card means in this test

The one-card server exposes only physical GPU0 through ROCR_VISIBLE_DEVICES=0. Its diffusion model, text encoder, video VAE and audio VAE all target cuda:0. System statistics verify exactly one visible device. The earlier saved reference placed the DiT on GPU0 and encoder/VAEs on GPU1; that was one-card denoising with two-card component placement. The new test is a true one-physical-card workflow.

The two-card arm reuses the previously validated davoddino-derived bounded host-staged TP2 implementation: two visible gfx1100 devices, split DiT, explicit 64 MiB pinned-host transport and acknowledged copies, with phase-owned encoder/VAEs. Native Radiance and the fcys forum source are not deployed by this comparison. Both peer directions remain unavailable; this path implements host transport.

## Common protocol

Same original checkpoint payloads and saved red-teapot prompt, 608×352, 39 frames, 24 fps, 20 steps, seed 42, res_multistep/simple, CFG1, SDPA and cache-none. Each generation gets a fresh server, unique owned scope and fresh model ownership. Each arm has one excluded full warmup and three timed requests. Server execution includes encoding/loading, sampling, decode and saving; server readiness and teardown are reported separately in lifecycle time. All requests use the same short system-disk TMPDIR. One-card runs precede two-card runs; this small ordered experiment is not a broad performance guarantee. Cold means fresh server/model ownership; OS file caches and system paging were not flushed or controlled. The standard one-card DiT reads the original Shared-SATA checkpoint, while the host-staged arm reads previously derived rank shards on the system disk. Both arms read the same original encoder/VAE payloads on Shared-SATA. Storage and loader differences therefore affect full-request latency; sampler time excludes those disk-loading phases.

The first one-card warmup completed in 229.485 s. Admission for the next fresh scope briefly found a lingering KFD driver entry after worker exit. The harness paused rather than launch through it; no client was killed. A bounded 30 s wait for driver release was added, the successful warmup was retained, and timed requests resumed. The wait applies to both arms and is outside server execution time. It does not relax device-idle, physical-memory or ownership admission.

## Guards and quality

Every generation keeps the 3 GiB available-RAM floor, 2 GiB free-VRAM soft floor for four samples, 1.5 GiB hard floor, physical-RAM scope cap, unlimited swap occupancy, zero dedicated VRAM spill, exclusive GPU/server locks and complete lifecycle thermal recording. Source-reader 3 GiB VRAM admission remains on the host-staged arm. Loading, parked swap and reads are permitted; rates and PSI are advisory, with no SSD-write budget configured. No existing inference task was stopped or unloaded. All owned workers and scopes exit and the GPU lock is released.

All eight saved 39-frame outputs pass complete ffmpeg AV decoding, 608×352/24 fps/frame-count checks and finite stereo 32 kHz PCM checks. Decoded video/PCM digests and sampled contact sheets are retained. Sampled first/last timed contact sheets from both arms show coherent red-teapot scenes, consistent lighting and steam without obvious corruption. Within each arm, all four outputs have different decoded-video and PCM digests; bitwise repeatability is not established for either path. Technical checks do not establish semantic audio quality or exhaustive motion quality.

## Attribution and current status

The two execution paths use different frozen Comfy source snapshots, CPU versus GPU initial-noise generation, original Shared-SATA DiT versus system-disk trial shards, and standard versus bounded phase loading/destruction. Same seed does not mean identical input noise or pixels. A lower total request time can coexist with slower sampling because loading/other overhead differs. The result therefore answers which tested cold workflow finished sooner on this host, without attributing every difference solely to adding a card. Three timed runs per arm provide medians and ranges; larger workloads, persistent-server behavior and maximum capacity remain unqualified.

This fresh result supersedes the earlier unavailable matched median in [the first host-staged report](H3-HOST-STAGED-2026-10-28.md). Its two repeated-request control RAM-floor failures remain valid historical evidence for that different lifecycle. Earlier 83.831 s and 210.098 s single-DiT references retain their original RAM/build/lifecycle attribution and are not substituted for these fresh measurements.

Production profiles, model payloads, engine pins and paused schedules remain. The candidate remains isolated; no automatic promotion is made.

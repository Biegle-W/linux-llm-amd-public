# Nemotron-3.5-Bolt on vLLM versus llama.cpp — October 21, 2026

The user asked to download the 4-bit vLLM build of Bolt found in the
[research note](VLLM-ALTERNATIVES-BOLT-SAGE-2026-10-21.md) and test it in isolation against the
current llama.cpp Bolt profile. **Neither profile was changed.** The vLLM build is stored on
sharedSATA2 and is not an active profile.

**Candidate:** [SergiioB AutoRound W4A16](https://huggingface.co/SergiioB/Nemotron-3.5-Bolt-74B-A9B-AutoRound-W4A16-G128-sym/tree/b9f381d20cbd4cede9f729c2647d2542c4a35997),
GPTQ int4, group 128, symmetric, 43.6 GB.
- All 32 files matched the publisher's checksums.
- Every bundled Python file, plus the tokenizer, chat template and processor files, is
  byte-identical to NVIDIA's official BF16 repo (rev `56702103`), so `--trust-remote-code`
  runs NVIDIA's code.
- NVIDIA's original generation config (two end-of-turn tokens) was used.

**vLLM arm**
- Engine: vLLM 0.32.1rc1.dev36 (ROCm 7.2.3, the production build), TP2 on both cards.
- Text only, BF16 KV, Triton attention, one sequence, compiled decode graphs.
- Isolated on port 18180 in a 52 GB no-swap memory scope.
- Weights took 18.9 GiB per card. Linear layers used the gfx1100 W4A16 kernel. The MoE experts
  used vLLM's Triton WNA16 kernel, because the local gfx1100 MoE kernel only accepts
  compressed-tensors checkpoints.

**Control:** the production `nemotron-3.5-bolt` profile (llama.cpp `4c3c5810`, HIP, Q4_K_M,
262K context, expert cache), started with the normal launcher.

**Method:** the shared benchmark method (`hardware/benchmark-current-amd.py`, unchanged):
- Arithmetic check.
- Excluded warm-ups, then three timed 256-token code and prose requests (temperature 0.6, seed 42,
  thinking off).
- Three fresh, salted ~7.9K-token, three-marker retrieval prompts.

| Bolt arm | Code / prose decode t/s | Short TTFT s, code / prose | Fresh ~7.9K prefill t/s | Fresh TTFT s |
|---|---:|---:|---:|---:|
| llama.cpp Q4_K_M (production) | 36.84 / 36.67 | 0.389 / 0.249 | 224.2 | 35.36 |
| **vLLM AutoRound W4A16** | **37.99 / 37.91** | **0.075 / 0.068** | **2,910** | **2.73** |

- **Decode:** effectively the same, +3%.
- **Prompt processing:** about **13× faster**, so the wait for an ~8K prompt drops from
  35 s to under 3 s.
- **Short-prompt TTFT:** 4–5× lower.
- **Checks:** both arms passed arithmetic and all marker checks, with zero swap and zero VRAM spill.

**Full window:** vLLM also started at **262,144** context, the same as the llama.cpp profile.
1.75 GiB of KV per card holds 406,323 tokens, with prefix caching on.
- A fresh **254,994-token** prompt retrieved all three markers. Time to first token was
  200 s, about 1,270 t/s at that length.
- The full-history follow-up (255,034 tokens) answered in 2.3 s.

**Thermals (sampled peaks)**

| Arm | GPU0 junction / VRAM °C | GPU1 junction / VRAM °C |
|---|---:|---:|
| vLLM | 89 / 68 | 76 / 68 |
| llama.cpp | 82 / 76 | 59 / 70 |

vLLM loads the second card more evenly.

**Not tested yet:**
- Tool calling and constrained JSON on vLLM (no tool parser was configured).
- Images and audio.
- Quality beyond retrieval and arithmetic.
- The gfx1100 MoE kernel, which would need a compressed-tensors repack and might raise decode
  speed.

Three trials per task are a screen, not a statistical proof.

**Conclusion:** the vLLM build is not faster at generating text. It is dramatically faster at
reading prompts, and it holds the same 262K window. Long agent or document prompts would benefit
most. It is a strong candidate for an added vLLM Bolt profile once tool calling and JSON pass.

Evidence: [numeric record](results/bolt-vllm-2026-10-21.json). Raw logs are in ignored
`hardware/generated/bolt-vllm-2026-10-21/`.

## Promotion — later October 21

At the user's request ("switch over, remove the slower alternative"), the vLLM build is now the
active Bolt profile `nemotron-3.5-bolt-vllm`, launched by `vllm/start-bolt-rocm` and served by the
normal vLLM router at 262,144 context. It uses NVIDIA's `qwen3_coder` tool parser and its
`ultra_v3` reasoning-parser plugin, with thinking off by default.

**Checks through the production launcher and router:** arithmetic, ordered JSON, a tool round trip
and a 100-integer JSON array all passed, with zero VRAM spill. Cold load plus compile took 262 s.

**Production benchmark (same method):** 37.32 / 37.21 t/s decode, 2,958.7 t/s fresh prefill,
2.69 s ~7.9K TTFT. Peak VRAM was 23.8 / 22.9 GiB with no swap or spill. Sampled GPU0/1 junction
peaks were 94 / 79 °C.

**Retired:** the llama.cpp `nemotron-3.5-bolt` profile, and the llama.cpp `qwen3.8-27b-q4`
profile, whose SGLang (212/73 t/s) and vLLM (134/71 t/s) versions are faster. Their GGUF files are
retained on sharedSATA1 until the user decides. llama.cpp now has four HIP profiles and no
Vulkan profile.

## Retained settings and actual GPU placement

Both models use HIP on **both** cards, one active request and one loaded model
at a time. GLM divides target layers `[0,24)` / `[24,45)`; its NextN block runs on
the second card. It uses MTP, a **40 GiB whole-machine pinned expert RAM ceiling**,
GPU hot-expert caches, cold NVMe reads, automatic prefill, sub-batches 1,024,
a 4 GiB prefill budget and streamed KV. The version-matched gfx1100 hipBLASLt
100202 table was accepted. The 40 GiB cap is divided across the two parts;
it is not a per-card RAM budget.

DeepSeek uses CPU-mapped GGUF expert backing, GPU hot-expert caches and the OS
page cache, with cold experts/Engram rows read from NVMe. Its non-GPU expert
address space is about 146 decimal GB at the initial reserve; that does **not**
mean 146 GB of resident system RAM. No experimental static `DS4_COPY_GB` tier is
selected. Its requested `--tp 2` is changed by the engine to width 1 because
256-value blocks cannot divide a 2,304-wide expert into two valid parts.
**Both GPU layer groups remain active. This is layer splitting, not true TP2.**
The native packed KV layout is FP4 for compressed KV/index keys and FP8 for the
window. Final selection is 24 CPU lane threads with **DSpark not loaded**;
the matching draft weights remain available on NVMe.

Both final configs request **8 GiB native VRAM reserve per card** and admission
checks **at least 6 GiB actual whole-card free at startup**. HIP's printed free
estimate omitted other desktop allocations: a native 6 GiB request left only
about 4.6–5.8 GiB whole-card free in the initial probes. Those initial settings
were not activated. A continuous latched guard retains the existing 3 GiB
RAM/VRAM floors, zero worker swap/spill, and unloads only its owned worker.
Workers have `MemorySwapMax=0` / `MemoryMax=52G`; admission requires 60 GiB
physical and 52 GiB available RAM after backend handover. No unrelated GPU app
is killed to manufacture headroom. Source, binary SHA, config fingerprint and
DeepSeek's Linux index hash must match validation. Quality-changing expert
skipping stays off.

## DeepSeek screening: speculation and CPU threads

These 8K screening cases used the **same native 6 GiB reserve**, 128-output cap,
three excluded warmups and three timed requests for each short code/prose task.
Sampling: temperature 0.6, top-p 0.95, seed 42, thinking off. Fresh ~7K marker
prefill is a separate greedy functional probe, not a three-trial PP median.

| CPU lane threads / draft | Code SSE decode t/s | Prose SSE decode t/s | Native fresh ~7K PP t/s | Composite relative to default |
|---|---:|---:|---:|---:|
| 24 / none, retained | 8.49 | 7.64 | 147.5 | 1.000 |
| 8 / DSpark on | 8.40 | 6.52 | 149.7 | 0.950 |
| 8 / none | 10.11 | 6.93 | 152.8 | 1.038 |

The declared rule required functional/tools/retrieval and guards on both cards,
then at least **5%** improvement in the geometric mean of code decode, prose
decode and native ~7K prefill to replace the baseline. Neither candidate passed
the improvement threshold. This does not prove 24 threads universally fastest.
Stateful caches were not flushed; the 8-thread cases used independent copies of
the same post-baseline routing seed, while the baseline evolved in place.
Three trials do not establish statistical significance or an isolated CPU/MTP
causal effect. Initial one-warmup results are retained separately and show large
warming effects. Final 32K desktop-reserve measurements are separate below;
do not substitute these screening speeds for production.

## Numerical and functional limits

The 14 documented GLM/kernel checks passed independently on each RX 7900 XTX.
The broader DeepSeek GGUF suite failed two **bit-exact** token/window comparisons
for mixed IQ4_XS/Q4_K and Q4_K/IQ4_XS on each card, although their numerical
CPU-reference comparisons passed. No tolerance/assertion was weakened. The actual
downloaded Maya-S index contains only BF16, F32, IQ2_S, IQ2_XXS, IQ3_S, IQ3_XXS,
MXFP4, Q6_K and Q8_0. Admission blocks other types and an altered index. These
selected-model checks do not establish support for the failing formats or all
AMD DeepSeek quants. DeepSeek's vision pack is installed but image-request
accuracy/performance is unvalidated; GLM is text only. JSON/tool checks use
synthetic stock results and never execute a model-requested external tool.

## Launch, API and Windows sharing

Use **Maya** on the Desktop or `llm-maya`; it starts only the backend in a visible
terminal. Start `dsh` separately, select **Local Maya**, then the exact model ID
in the final table. The saved DSH default remains Strata. Router/worker are
loopback **30030/30031**; LAN/Tailscale clients use the existing authenticated
**port 10000 `/v1`** gateway. Switching model IDs unloads the previous Maya model;
existing backend handover stops only configured inference and owned workers.
DSH, the gateway, ComfyUI and unrelated applications remain running.

[Preparation/install notes](../maya/README.md) distinguish upstream installer
outputs from guarded production launchers. GGUF weights may be shared with
Windows. Maya's generated DeepSeek index contains a Linux absolute model path;
Windows must generate its own **separate pack/index**, without overwriting the
Linux index. The new shared NVMe's Windows letter is unknown. The canonical
[Linux/Windows handoff](../network/LINUX-LLM-RUNTIME-HANDOFF.md) remains on Shared SATA / D:.

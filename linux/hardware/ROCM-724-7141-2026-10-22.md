# ROCm 7.2.4 and 7.14.1 versus the retained 7.2.3 — October 22, 2026

The user asked whether updating ROCm would help anything, and later asked to include
Ornith-1.5-122B and Sage-A1.5. **Answer: no.** Every candidate stayed within about ±3% of a
fresh 7.2.3 control. The only borderline result (Sage on 7.14.1) disappeared under other seeds.
**ROCm 7.2.3 is retained everywhere.** No production setting changed.

## What was available

- **10.1.0** (October 5) is still AMD's latest official release. All six engines were tested
  on it on October 21, and no candidate passed
  ([report](ROCM101-2026-10-21.md)).
- **7.2.4** (May 29) is a patch on the 7.2 line. Its main change is lower `hipGraphLaunch`
  latency.
- **7.14.1** (September 2): an official TheRock gfx110X tarball
  (`repo.amd.com/rocm/tarball-multi-arch`, 2.31 GB, SHA-256 recorded). Its only PyTorch wheels
  are 2.10, older than the ones the installed vLLM/SGLang were built against, so only native
  engines can be tested fairly.

## Method

**7.2.4:** the five 7.2.4 runtime packages (HIP, HSA, COMgr, rocprofiler-register, rocm-core)
were downloaded from `repo.radeon.com` and checked against AMD's SHA-256 values. They were
placed ahead of the 7.2.3 libraries through a new opt-in `LOCAL_ROCM_RUNTIME_OVERLAY` hook in
`hardware/rocm-env.sh` (unset in production). The engine binaries and every other library
were unchanged. Each arm recorded the `libamdhip64` it actually loaded.

**7.14.1:** llama.cpp `4c3c5810` was rebuilt with the production CMake flags against the
7.14.1 SDK, using all of that SDK's HIP and BLAS libraries.

**Ornith** used its own test harness, which gained `--sdk 724/7141` options. Its 10.1 arm reused
the October 21 build.

**Every arm:**
- Started through the normal launcher, or the Ornith harness, under the GPU lock.
- Measured with the shared benchmark method: three timed code and prose requests, three fresh
  ~8K marker prompts.
- Compared with a fresh 7.2.3 control from the same session.

**Gate:** more than 3% geometric-mean gain over {code decode, prose decode, fresh prefill},
with no phase more than 5% worse.

## Results

| Profile | Candidate | Code / prose / prefill vs 7.2.3 | Change | Decision |
|---|---|---|---:|---|
| vLLM Qwen3.8-27B (MTP3) | 7.2.4 runtime | 0.995 / 0.994 / 0.999 | −0.39% | Retain 7.2.3 |
| llama.cpp Qwen3.6-35B-A3B | 7.2.4 runtime | 0.984 / 1.001 / 0.999 | −0.56% | Retain |
| llama.cpp Qwen3.6-35B-A3B | 7.14.1 rebuild | 0.986 / 1.020 / 0.997 | +0.09% | Retain |
| llama.cpp Sage-A1.5 | 7.2.4 runtime | 0.998 / 1.003 / 0.997 | −0.09% | Retain |
| llama.cpp Sage-A1.5 | 7.14.1 rebuild, seed 42 | 1.024 / 1.074 / 0.997 | +3.13% | Borderline; confirm |
| llama.cpp Sage-A1.5 | **7.14.1, seeds 42/43/44 mean** | 1.025 / 1.025 / **0.950** | **−0.05%** | **Rejected** |
| Ornith-1.5-122B (MTP off, 32K) | 7.2.4 runtime | 0.999 / 0.999 / 1.000 | −0.06% | Retain |
| Ornith-1.5-122B | 7.14.1 rebuild | 0.989 / 1.016 / 0.991 | −0.12% | Retain |
| Ornith-1.5-122B | 10.1 build | 0.988 / 1.013 / 0.991 | −0.27% | Retain |

**Sage on 7.14.1.** The seed-42 prose gain came partly from a low control (65.3 t/s). The 7.2.3
seed-43/44 controls ran at 67.7/69.2. Meanwhile the later 7.14.1 runs read prompts at about
357 t/s against 385 on 7.2.3. Decode is about 2.5% faster on 7.14.1 and prefill is 5% slower,
so it is not an improvement.

**Ornith:** speed is limited by moving its CPU-resident experts. All four versions land within
about 1% (11.3–11.5 / 13.3–13.5 t/s decode, 52.2–52.7 t/s prefill).

**Checks:** all arms passed arithmetic and every marker check, with zero worker swap and zero
VRAM spill. Sampled GPU0/GPU1 junction peaks were up to 94/81 °C under vLLM and 66–86/52–60 °C
under llama.cpp.

## Not tested, and why

- **SGLang on 7.2.4, and Bolt vLLM:** GNOME Shell held about 2.2 GiB on GPU0 during these runs.
  That left 22.37 GiB free, below SGLang's 22.75 GiB admission limit and Bolt's ~22.6 GiB need,
  so both backends correctly refused to start. Normally the desktop runs on the Intel iGPU.
- **vLLM/SGLang on 7.14.1:** no matching PyTorch wheels (see above).
- **Strata/Maya:** their launchers set their own library paths. Both were tested on 10.1
  yesterday and retained 7.2.3.

## Community evidence

As recorded in the [ROCm selection note](ROCM-SELECTION-2026-10-21.md),
[Ben Lee on lcz.me](https://lcz.me/topic/1532/95) reported SGLang dual-XTX decode of
62.2/66.4/74.1 t/s on 7.2.3/7.14/10, with slower prefill on 10. Our matched 10.1 SGLang test was
−0.82%, and SGLang could not be retested today. [Level1Techs' AMD source collection](https://forum.level1techs.com/t/the-twisted-links-of-amd-ai-collection-of-useful-links-for-amd-ai-dev-and-deployment/244053)
lists the TheRock locations used here. Neither source supports a local speed claim.

## Side fixes made during this test

- `dsh/launch-backend.py`: the vLLM/SGLang backend start check now uses the *least*
  demanding profile's VRAM requirement. Adding Bolt (22 GiB) had raised the backend-wide check
  above Qwen's 21 GiB. The router still enforces each profile's own requirement before loading.
- `hardware/rocm-env.sh`: the opt-in `LOCAL_ROCM_RUNTIME_OVERLAY` hook described above.

Evidence: [numeric record](results/rocm-724-7141-2026-10-22.json). Raw logs, the 7.14.1 SDK and
build, and the 7.2.4 packages are in ignored `hardware/generated/rocm-724-7141-2026-10-22/`.

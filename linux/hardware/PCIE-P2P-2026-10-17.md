# PCIe P2P diagnosis and solution — October 17, 2026

## Finding

The current i5-13600KF / MSI MPG Z690 CARBON WIFI layout cannot expose a supported
cross-root-port P2P path to the two RX 7900 XTX GPUs. **No software-only fix was
validated.** TP2 remains functional through the retained RCCL host transport.
The proposed hardware remedy is a **transparent active PCIe switch with both GPUs
below one common switch**, keeping peer transactions out of the CPU root complex.
That hardware is not installed here; no P2P throughput improvement is claimed.

## Evidence from this workstation

- GPU0 path ends at CPU graphics root port `0000:00:01.0`; GPU1 ends at
  `0000:00:01.1`. Both currently operate at PCIe 4.0 x8.
- At boot, amdgpu reports in both directions: `PCIe P2P access from peer device
  ... is not supported by the chipset`. This is a topology rejection before
  SGLang, vLLM or RCCL starts.
- The driver parameter `pcie_p2p` is already enabled. Both GPUs have 32 GiB BAR0
  mappings. Kernel `PCI_P2PDMA`, `HSA_AMD_P2P` and `DMABUF_MOVE_NOTIFY` are enabled.
- The CPU host bridge is `8086:a704`. Upstream Linux v7.0's P2PDMA host allowlist
  does not contain that bridge. amdgpu's peer check calls `pci_p2pdma_distance()`;
  a negative result triggers the observed chipset message. The upstream code
  explains the rejection; the complete Ubuntu kernel source was not rebuilt.
- HIP enumerates both GPUs but reports peer capability false in both directions.
  KFD exposes GPU-to-CPU links and no GPU-to-GPU IO link.
- The running system has Intel IOMMU in translated mode. ACS register controls
  were not readable without administrative authentication. Their exact state is
  not claimed to be known, and changing them was not necessary to identify the
  CPU's documented graphics-port limitation.

The [Intel processor datasheet](https://edc.intel.com/content/www/us/en/design/products/platforms/details/raptor-lake-s/13th-generation-core-processors-datasheet-volume-1-of-2/pci-express-support/)
lists P2P memory reads and writes as unsupported for the S-series PEG10/PEG11
graphics ports used by this configuration. This provides a hardware reason to
retain the kernel restriction rather than assume the missing allowlist entry is
merely an oversight. This finding is specific to these ports and processor line;
it is not a claim that every Intel platform or RX 7900 XTX lacks PCIe P2P.

## Reversible options tested

Each case ran in a fresh process, with `NCCL_P2P_DISABLE` removed. No GPU buffers,
inference workers or system changes were needed for the HIP capability query.

| Process-local settings | GPU0 → GPU1 | GPU1 → GPU0 |
|---|---|---|
| Default HSA settings | Unavailable | Unavailable |
| `HSA_FORCE_FINE_GRAIN_PCIE=1` | Unavailable | Unavailable |
| Fine-grain PCIe plus `HSA_ENABLE_SDMA=0` | Unavailable | Unavailable |

HIP returned success for each query, with capability value zero, rather than a
runtime API error. Since the driver exposes no peer route, direct transfer and
P2P collective tests were not attempted. No inference speed benchmark was rerun.
See [sanitized measurements](pcie-p2p-2026-10-17.json).

`hardware/check-pcie-p2p.py` reproduces the capability/topology checks with the
existing private HIP runtime. Example from the runtime workspace:

```bash
python3 hardware/check-pcie-p2p.py
```

The utility is diagnostic only. It does not enable peer access, benchmark bandwidth,
write PCI registers, alter IOMMU/ACS, unload drivers or change boot configuration.

## Recommended hardware route

Both GPUs must be downstream of the **same real switch**, for example a properly
configured Broadcom PEX88000-family PCIe 4.0 GPU expansion board. This is a class
of hardware to verify, not a validated seller listing or purchase authorization.
Broadcom describes the [PEX88048](https://www.broadcom.com/products/pcie-switches-retimers/expressfabric/gen4/pex88048)
as a Gen4 switch capable of transparent fan-out; the complete expansion board's
firmware, slot wiring, cables and power delivery still need checking.

Target topology:

```text
CPU → PCI_E1 → active PCIe switch
                  ├─ downstream port → RX 7900 XTX #1
                  └─ downstream port → RX 7900 XTX #2
```

Requirements before choosing a board:

1. Transparent single-host PCIe switching with documented local endpoint-to-endpoint
   P2P. A passive x8/x8 splitter, bifurcation adapter or retimer does not add routing.
2. PCIe 4.0 upstream and at least x8 to each GPU. A Gen3 switch can reduce link
   bandwidth compared with the existing Gen4 x8 connections.
3. Enough 64-bit MMIO space for both large GPU BARs, with Above 4G decoding and
   ReBAR preserved. Confirm GPU/display initialization on this motherboard.
4. Downstream ACS settings that allow local peer traffic. Redirecting peer traffic
   back to the CPU defeats this topology's purpose. Inspect the real configuration
   before changing ACS; do not apply a blanket override.
5. Correct powered GPU risers/slots, matching cables, cooling and room for both
   cards. The switch itself must also be powered and cooled as its vendor specifies.

MSI documents [PCI_E1/PCI_E2 as x16/x0 or x8/x8](https://us.msi.com/Motherboard/MPG-Z690-CARBON-WIFI/Specification).
For an external switch attached to PCI_E1, keep PCI_E2 electrically unused so the
switch can receive the full CPU x16 link. Both GPU connections then come from the
switch. The CPU's x16 host link is shared, while local GPU-to-GPU traffic can stay
within the switch. This is an expected topology benefit, not a measured speedup.

The [Linux P2PDMA documentation](https://docs.kernel.org/driver-api/pci/p2pdma.html)
explains why a common switch can work without relying on unsupported cross-root
forwarding. A different CPU/motherboard with a validated P2P path is another route,
but requires a platform replacement rather than a launcher adjustment.

## CPU upgrades on this motherboard

MSI lists 12th, 13th and 14th Gen Core CPU support for this LGA1700 board.
There is no documented supported drop-in CPU upgrade recommended here to enable
GPU P2P. The cited Intel datasheet covers the 13th/14th Gen S-series graphics-port
limitation, so a 13900K/14900K upgrade does not provide the documented routing
capability needed. This investigation did not individually test every supported
CPU. Keep the 13600KF if retaining this platform and pursuing the switch route.

## Activation after hardware changes

1. Confirm `lspci -t` shows a common switch upstream of both GPUs. Repeat the probe;
   require peer capability in both directions and adequate BAR mappings.
2. Verify real bidirectional data integrity, direct GPU-kernel access and HIP IPC.
   A successful copy call alone may use host staging and is insufficient evidence.
3. Test the retained RCCL library with P2P enabled in an isolated process. Inspect
   RCCL logs for the actual transport; do not assume capability means RCCL uses it.
4. Validate FP32/BF16 all-reduce/all-gather, then model arithmetic, JSON, tool calls,
   memory residency and matched-workload throughput before changing defaults.

Current production settings retain `NCCL_P2P_DISABLE=1`, `HSA_ENABLE_SDMA=0`, custom
all-reduce disabled and the isolated no-hostcall RCCL library. Removing the P2P flag
does not fix the driver topology rejection. The RCCL hostcall compatibility issue
is separate from P2P and must not be assumed fixed by a future switch.

## Other approaches evaluated

- ReBAR is already large enough; toggling it is not the missing fix.
- IOMMU/ACS changes alone do not establish unsupported CPU forwarding. No boot
  parameters or security isolation were changed, and no reboot is required now.
- Adding `8086:a704` to the kernel allowlist or overriding amdgpu's check would
  advertise an unvalidated route. The processor documentation provides no basis
  for deploying that bypass. No kernel patch was installed.
- `pci=pcie_bus_peer2peer` controls maximum payload sizing; it does not create a
  root-complex routing path or add this CPU to the allowlist.
- The [lcz.me X99 switch discussion](https://lcz.me/topic/1791) includes switch
  and custom-kernel experiments on different Intel platforms. It is useful context,
  not validation of Raptor Lake S cross-root P2P.

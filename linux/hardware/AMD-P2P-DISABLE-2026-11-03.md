## Active disable and checks

Both boot options `amdgpu.pcie_p2p=0 amdgpu.use_xgmi_p2p=0` are active; loaded flags read `N` / `0`. The former authenticated managed ACS/IOMMU peer-routing policy was withdrawn. All six selected bridges read ACS `0x1d`; both GPUs have translated IOMMU domains. KFD exposes two GPUs and no GPU-to-GPU links.

Three fresh HIP processes (default, fine-grain PCIe, fine-grain/no-SDMA) each report capability zero in both directions and refuse both enable calls. The [checker](verify_amd_p2p_off.cpp) validates both distinct PCI devices before interpreting refusal. CLR 7.2.3 returns `hipErrorInvalidDevice` when the valid-device capability query returns zero; the checker accepts this source-verified path or `hipErrorPeerAccessUnsupported`, while other errors fail. An initial checker-only stop expected the generic unsupported code; source review corrected it before the only model-load attempt. See [matching CLR source](https://github.com/ROCm/clr/blob/rocm-7.2.3/hipamd/src/hip_peer.cpp#L172-L180).

Kernel flags gate KFD topology/VRAM mappings; DMA-buf sharing uses a separate PCI routing check, so routing was restored too. See [kernel parameters](https://kernel.org/doc/html/latest/gpu/amdgpu/module-parameters.html), [peer gate](https://github.com/torvalds/linux/blob/v7.0/drivers/gpu/drm/amd/amdgpu/amdgpu_device.c) and [DMA-buf implementation](https://github.com/torvalds/linux/blob/v7.0/drivers/gpu/drm/amd/amdgpu/amdgpu_dma_buf.c). Host-staged transfers remain valid; this is not a claim about every hypothetical privileged DMA implementation.

The normal ROCm environment retains transport P2P disable and unsets `GGML_CUDA_P2P`. The llama launcher no longer opts models into that presence-based switch, including inherited `=0` values. Model settings, both-GPU visibility, source pins and resource/SSD policies are retained. No engine rebuild or promotion occurred.
